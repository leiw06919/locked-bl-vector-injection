# 判据：什么叫"真成功"

> 整个过程里最贵的教训不是"怎么打通"，是"怎么确认自己通了"。
> 我们至少两次以为成功了，其实没有。

---

## 1. 四行日志

框架注入的完整链路会打出这四行，缺任何一行都不算成功：

| # | 日志 | 证明什么 |
|---|---|---|
| 1 | `System Server died` | zygote 真的重启了，不是假信号 |
| 2 | `Got system server binder via serial on attempt 1` | daemon 切名成功，新的 system_server 找到了它 |
| 3 | `Injected Vector framework into system_server` | 注入动作真的执行了 |
| 4 | `Successfully injected Vector IPC binder for applications` | 应用侧能拿到 binder，**这一行才是终点** |

注意第 4 行和第 3 行的区别：第 3 行只说明"注入了"，第 4 行才说明"能被应用用"。只有前 3 行的情况出现过，表现是管理器看起来正常、但所有模块都不生效。

---

## 2. 交叉验证：去目标进程里看

日志是当事人自己说的，会有主观性。硬证据在进程的地址空间里：

```
/proc/<target_pid>/maps
```

应能看到模块注入的 `.so`。本次的实测结果是：

```
libxr_stealth.so                 ← XRadiant 的 stealth 库
libquickjs-android-wrapper.so    ← 它的脚本引擎 wrapper
```

这一条比任何日志都可靠，因为它不受框架自己的状态机影响。

以支付宝为例，注入成功后应该看到 **5 个进程**全部命中：

```
tools
push
gpu_process
widgetProvider
sandboxed_privilege_process0
```

只命中其中一个（尤其只有 `tools`）通常意味着注入只完成了一半。

## 3. 三层判据体系

按可信度从低到高：

| 层 | 证据 | 可信度 | 常见误判 |
|---|---|---|---|
| 第一层 | 框架内部状态标志（如 `isFdAttached`） | **低** | 会先变 true，但注入可能仍然失败 |
| 第二层 | 四行日志 | 中 | 日志被缓冲区冲掉后读不到，会误判为失败 |
| 第三层 | 目标进程 `/proc/<pid>/maps` + 模块实际行为 | **高** | 无 |

**结论**：只信第三层。第一层是长期假信号，第二层会因日志滚动而失效。

---

## 4. 已知的两个假信号

### 假信号 A · `isFdAttached`

框架内部用它表示"文件描述符已挂上"，这个标志**在注入真正成功之前就会变 true**。我们曾据此判断成功，结果模块一个都没加载。

### 假信号 B · 日志被冲掉

日志缓冲区是环形的。设备开机久了之后，早期的注入日志会被冲掉，`grep` 出来是全空——**但这不代表没注入**。

表现：同样的命令，刚恢复完时四行齐全，几小时后一条都没有，而进程 maps 里的 `.so` 一直都在。

**对策**：
- 判断"现在是否生效" → 看 maps 和进程 pid
- 判断"刚才这次注入是否成功" → 在**同一次会话内**立刻抓日志，不要隔几小时回头看

---

## 5. 时间窗口

这套判据有一个隐藏前提：**只在刚完成注入的几分钟内可靠**。

超过这个窗口，你面对的是"三层证据里最可靠的那层还在、另外两层都不可用"的状态。这时候：

- 不要因为日志空了就重跑一遍流程（重跑有成本，会先杀掉正在工作的 daemon）
- 直接用 maps 验证；maps 对了就是对的

---

## 6. 一句可迁移的话

> 判断一个"注入类"操作是否成功，永远不要相信操作者自己报告的状态；
> 要去被注入者那里，看它的地址空间里到底有没有东西。

这条规律适用于所有 hook / 注入 / 插桩场景，与具体框架无关。
